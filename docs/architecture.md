## 1. 設計方針と選択肢

既存HTMLを分割移植せず、「曲データ」「同期セッション」「外部入出力」「表示」の責務で再構成する。単一のフロントエンドで開始し、サーバー、DIコンテナ、イベントバス、モノレポ、汎用プラグイン機構は導入しない。

| 選択肢 | 利点 | 負担・弱点 | 判断案 |
| --- | --- | --- | --- |
| JavaScript＋DOMのみ | 依存が最少、現在に近い | 型での状態制約が弱く、描画整合性を手で管理 | 小試作には可 |
| TypeScript＋Vite、UIフレームワークなし | 型、単体テスト、静的配布が使え軽量 | UI更新・イベント破棄を自作 | 画面を極小に保つ代替案 |
| TypeScript＋React＋Vite | 状態に基づく描画、部品単位の検証、周辺ツール | 依存・学習負担、Effect二重実行対策 | 採用確定。停止・準備・エラー表示の整合性を重視 |
| SSR/フルスタック構成 | サーバー機能を統合可能 | 本用途はブラウザAPI主体、サーバー保守が過剰 | 初期版では採用しない |

TypeScript＋React＋Vite、Vitest・Playwrightによる自動テストを採用する（Q-11確定）。strict、Testing Library、ESLint、純粋なreducerと小さなcontrollerは具体化案。Redux/XStateは初期採用しない。状態遷移が増えた場合のみ専用ライブラリを再検討する。無料のローカル開発・テストを優先し、有料サービスやAI APIを必須依存にしない。既存端末・回線・将来の署名配布等まで無償と保証するものではない。

Windows＋Node.jsの導入時点のサポート中LTS＋npmを想定。Node/依存版を実装開始時に互換確認して固定しlockfileを管理。現環境でnodeは見つかったが、依存導入・npm/ブラウザ実行検証は今回していない。HTTPSでスマートフォンから開ける検証URLを用意する。ビルド出力は静的ホスティング可能とする。

## 3. 責務と依存

```text
UI → SessionController → 純粋な状態遷移・domain
                    → Player / AudioInput / SongRepository
起動処理 → 各adapterを生成してcontrollerへ渡す
各adapter → 正規化した結果・イベント → controller → UI
```

domainはDOM、YouTube、React、ストレージに依存しない。controllerは具体的なブラウザAPIを直接呼ばず、必要最小限のインターフェースを受け取る。インターフェースのための共通基底クラスは作らない。

将来の自動位置合わせは「位置候補→ユーザー確認→プロフィール保存」の入口を手動調整と共用する設計とする。候補にはprofileKey、位置、手法、任意の信頼度を持たせ、直接playや待機解除を起こさない。初期版は手動入力だけを実装する予定で、未使用の照合エンジンや汎用プラグイン基盤は作らない。YouTube音声の直接取得を前提とせず、参照素材・権利・照合可能性はN-06で別途検証する。

| モジュール | 責務 | 持たない責務 |
| --- | --- | --- |
| domain | ID・数値検証、開始位置、RMS・検知条件、データ変換 | 画面描画、端末取得 |
| session | コマンド順序、キャンセル、待機許可、再生意図 | 波形計算、localStorage詳細 |
| youtube | API読込、cue/play/pause、状態/エラー正規化 | 検知成立の判断 |
| audio | 権限、Context、波形、入力終了、解放 | 動画再生、曲保存 |
| storage | スキーマ検証、読書き、移行・復元 | 画面操作、マイク制御 |
| UI | 状態表示とユーザー意図を送信 | Promise完了を直接再生命令へ変換 |
| diagnostics | 時系列と原因、端末情報の任意出力 | 音声の常時録音、秘密情報収集 |

Reactの再描画やEffect再実行でマイクを開始しない。開始・停止はcontrollerの明示コマンドから行い、購読解除とdisposeは何度呼んでも安全にする。

## 4. YouTube制御

Player窓口はinitialize、prepare(videoId,startSec)、play、pause、seek、getPosition、disposeと状態購読程度。YouTube APIはplayがPromiseで成功確認できると仮定せず、イベントと期限で確認する。

- APIスクリプトのロード失敗・期限超過を分類。ローカル曲管理の初期化は独立させる。
- prepareはcueを使用し、対象動画に対応するCUEDを確認。動画バッファ準備完了とは解釈しない。
- autoplayを有効にせず、playsinlineと配信元originを設定。正規プレイヤーを可視で配置し最低サイズ要件を守る。
- R-01に従い、prepare中にplay/seekによる予備再生を行わない。無音の隠れた予備再生も初期案に含めない。
- PLAYING、PAUSED、ENDED、BUFFERING、onAutoplayBlocked、エラー2/5/100/101/150/153を正規化する。
- play要求とPLAYING受信を分離。PLAYINGはイヤホンでの発音時刻の証明にはならない。
- イベントは動画ID・世代と照合する。APIイベント自体に要求IDがないため、古いイベントが曖昧な場合は成功扱いにせずprepareをやり直す。必要ならプレイヤーを破棄・再生成する。
- 停止後にPLAYINGが遅着したらpauseを再発行。確認期限内に止まらなければプレイヤーを破棄してエラー表示。ブラウザ/OS障害下での物理的な瞬時停止は保証しない。

YouTube標準操作は隠して制約を回避しない。待機中に想定外のPLAYINGが来た場合は待機を解除し安全側にpauseする案。標準操作とアプリの意図の区別はN-03。一時停止後のアプリの「再生」は現在位置からのplayで、cue/seekを発行しない（確定）。

### 自動再生の成立性（レビュー改善案・V-05）

音検知コールバックはユーザーの直接操作ではない。「検知を準備」のタップやAudioContext.resume成功が、後のYouTube有音再生を許可するとは仮定しない。playsinlineやiframeのautoplay許可設定も成功保証ではない。IFrame越しに内部videoのPromiseやユーザー有効化状態を直接観測できると仮定せず、onAutoplayBlocked、状態イベント、期限、実音を組み合わせる。

実機では同一iPhone Safari・正規埋込可能動画を使い、次の軸を分ける。探索値は新たな合格仕様ではない。

- 初回/再訪、マイク許可未取得/取得済み、準備タップのみ/ユーザーが明示的に手動再生・一時停止した後。手動再生経験の有無を混ぜない。
- armed移行から検知まで0・5・30・120・240秒を探索し、実測の待機時間と最後のユーザー操作からの経過時間を別記。5分の待機上限と境界試験は別途実施する。
- Bluetooth事前接続、準備後接続、切断・再接続、本体出力の対照。経路変更で解除した場合は新たに準備し、旧セッションを再開しない。
- マイク保持/解放、冷起動/繰返し、同じプレイヤー/再生成。マイク取得・検知が実際に成立したかも確認する。

最初は代表条件で成立性を確認し、不成立に関係する軸を重点比較する。全組合せの網羅を段階2着手条件にしない。手動再生はユーザーが選んだ比較試験として可視で実行し、隠れた予備再生や毎回の事前発音を解決策にしない。

| 原因分類 | 根拠・切分け | 次の判断 |
| --- | --- | --- |
| ブラウザの再生ブロック | onAutoplayBlockedを記録、同条件の明示タップ再生と比較 | タップ後や短い待機だけで成功する条件を記録。イベントだけで内部の拒否理由までは断定しない |
| 実装・配信設定 | play未発行、古い世代、CUED前、API未読込、origin/iframe許可/Referer、153 | 正規の設定・順序を修正して再試験。nativeへ早合点しない |
| 動画・通信・プレイヤー | 埋込不可、非公開、APIエラー、BUFFERING、広告、開始期限超過 | 別の埋込可能動画・安定回線で比較。イベント不足の期限超過は原因未確定とする |
| 音声入力・出力経路 | 検知がない、Context停止、PLAYINGでもイヤホン無音/別経路 | 入力成立と実出力を検証。PLAYINGだけで自動再生成功としない |
| 精度・開始安定性 | 再生するが実音ずれやばらつきが目標外 | 固定ずれと変動、分析とプレイヤー/経路を分けN-01で評価 |

通常の初期準備後、実際の待機時間とBluetooth条件で安定して検知→自動再生できる場合はWeb継続候補。設定不備なら先に修正。毎回検知後にタップが必要、隠れた先行再生が必要、または対応条件で安定しない場合は中心要件未達としてUI拡充前に判断を戻す。許容する初回手動準備の範囲はN-09で確認する。

Web制約が主因ならnative連携の最小試験を検討するが、WebViewのメディア設定、YouTubeの埋込・動画制限、実発音の安定性を同じ条件で再試験する。native化だけで必ず解決するとは仮定しない。不成立なら範囲見直しもユーザー判断であり、自動開始要件を黙って手動再生へ置換しない。

根拠: [YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference)はブラウザによるscripted playbackのブロックを通知する。Safariの基礎的な有音再生制約は[WebKitのiOS方針](https://webkit.org/blog/6784/new-video-policies-for-ios/)を参照。ただし後者は2016年の説明であり、現在のiPhone/YouTube全組合せの証明ではない。2026-10-18に公式資料を確認し、現行対象版はV-05で実証する。

## 5. マイク・検知

AudioInputはacquire/release、稼働状態、RMS/時刻イベント、入力終了イベントを提供する。Detectorはarm/disarmと検知通知を持つ。検知処理停止とマイク解放は別操作とし、stream/Contextの所有者は常に1つにする。検知後の保持/解放方針はV-02待ちで固定しない。

起動はgetUserMedia→Context生成/必要時resume→running確認→検知開始。取得失敗時は途中資源も解放。echoCancellation/noiseSuppression/autoGainControlのfalseは要求であり強制成功と扱わず、track.getSettingsの取得可能値を記録する。未対応環境を識別する。

最小技術検証の比較基準はAnalyserNode＋requestAnimationFrame、2,048サンプル窓とする。しきい値0.08、継続時間50msを新規設定の暫定初期値とし、旧設定移行時は0msを候補とする。窓と描画周期が±0.05〜0.1秒の目標に無視できないため、フレーム間隔、サンプルレート、窓長、分析→通知遅延を記録する。rAF方式は製品版採用確定ではない。

AudioWorkletは描画に依存しない分析とサンプル単位の時間管理が利点だが、メッセージ遅延・実装負担が増え、YouTube起動精度を保証しない。V-04でrAFの揺れが誤差予算を圧迫するなら早期に比較試験する。分析が最大原因でなくても精度目標に寄与するか評価する。WorkletだけでBluetooth/ネットワーク遅延を解決した扱いにしない。

音量しきい値＋継続時間、0msから調整可能なのは確定。判定案はRMSがthresholdを厳密に超えた有効観測を起点に、durationMs以上連続した時に成立。0msなら最初の超過で成立。しきい値以下、入力中断、観測間隔100ms超（暫定）で継続をリセットし、rAF停止中の時間を持続音として数えない。比較条件、窓、間隔上限、初期値はV-08で検証する。ヒステリシスは未採用候補。

波形は既定で保存せずメモリ上で分析し、成立後はDetectorを終了して1回だけ再生要求する。継続時間は意図した検知遅延を加えるので、変更時は再キャリブレーションを案内する。マイク保持は検知とは独立した資源状態。

## 6. 非同期処理・状態管理

主状態案: idle、preparing、armed、starting、playing、paused、ended、stopping、error。別に選択曲・機種、desiredPlayback、micStatus（off/acquiring/running/retained/releasing）、playerStatusを保持する。マイク保持と検知中を同じbooleanで表さない。以下の終了・競合・失敗時の具体化はレビュー改善案RV-02〜RV-04であり、Qの追加確定ではない。

| 現状態・イベント | 次状態 | 作用 |
| --- | --- | --- |
| idle/paused＋準備 | preparing | 世代更新、設定をスナップショット化、マイクと動画を準備 |
| preparing＋全準備完了 | armed | 有効世代でのみ検知イベント受付 |
| preparing＋停止 | stopping→idle | 世代無効化、遅着資源の解放 |
| armed＋検知 | starting | 即座に待機解除、playを1回発行 |
| starting＋有効PLAYING | playing | 再生中を表示、マイク保持方針適用 |
| starting＋ブロック/期限超過 | error | pause、資源解放、手動操作を案内 |
| playing＋一時停止 | paused | 再待機せずpause確認 |
| starting＋一時停止 | paused（停止確認中を併記） | 再生要求番号を無効化、desiredPlayback=false、pause。遅着PLAYINGにもpause、マイク状態は変更しない |
| paused＋再生 | starting→playing | 現在位置からplay。cue/seek/armは行わず、PLAYINGを確認 |
| playing/starting＋有効ENDED | stopping→ended | 待機/再生意図を解除、検知終了、保持中マイクも解放。資源終了確認後に「再生終了」 |
| preparing＋許可拒否/取得期限 | stopping→error | 世代無効化、部分取得資源を解放、遅着streamも解放。自動再試行なし |
| armed＋待機期限超過 | stopping→idle（期限理由） | 世代無効化、検知/タイマー解除、pause、マイク解放。再開は明示準備 |
| 任意＋すべて停止/切替/離脱 | stopping→idle | 再生意図解除、検知停止、pause確認、マイク解放 |
| 任意＋旧世代の完了 | 状態維持 | 結果を破棄。資源なら解放 |

セッションごとに増加するgenerationを使う。stopは最初に世代と再生意図を無効化してから非同期解放を行う。getUserMedia自体をAbortSignalで取り消せると仮定しない。取り消せないPromiseの完了時に世代を照合してstreamの全trackを止める。旧rAF/タイマー/購読も解除し、解除に失敗しても世代チェックで無効にする。

開始中の連打は新しい開始を積まず、準備中表示と停止を提供する。再開始は前セッションの解放確認後。設定変更はarmed中に即適用せず解除→再準備する案。曲だけでなくDAM/JOYSOUNDの切替もセッション終了を経て行う。保存操作と再生セッションのスナップショットを分ける。一時停止は動画だけで、マイク状態を変更しない。マイクを保持していた場合もDetectorは終了状態を維持する。

一時停止では再生意図を先に解除し、直前のplayによる遅着PLAYINGもpauseで抑止する。続きから再生する明示操作は新たな再生意図として扱う。検知からの自動再生要求1回という制約と、ユーザーの明示再開を区別する。これにより一時停止の競合対策のためにマイクを解放・再取得する必要を作らない。

play要求の増加番号をgenerationとは別に持ち、starting直後pause→遅着PLAYINGと新たな明示再生を区別する。YouTubeイベント自体に要求番号はないので、現在意図と対象動画を照合し、曖昧なら成功とせずpause確認を優先する。ENDEDも現セッション・対象動画に限って扱い、旧イベントで新しいセッションのマイクを解放しない。重複終了・解放は冪等。自然終了後の再生位置と再準備導線はN-03で判断する。

拒否・期限・自然終了では解放完了と検知解除を別に追跡する。Context.close失敗や生きたtrackが残る場合は終了済みと偽らず、解放失敗表示と再停止を提供する。許可拒否でstreamがないケースも、既に作ったContext/購読/タイマーがあれば解放する。

期限値は次節の一元設定を参照する。テストの仮想時計で期限超過を検証し、本番値を都合よく縮めない。再生開始期限はハング検出用であり、精度の許容差ではない。

## 7. データ構造と永続化

共通の曲情報と機種別プロフィールを分離する（Q-08確定）。まだ新形式をリリースしていないため、新設のschemaVersion=1内で再設計し、存在しない旧設計版の移行処理は作らない。

| データ | フィールド案・制約 |
| --- | --- |
| Library | schemaVersion=1、revision、songs配列、legacyImportPolicy（候補提示可/自動候補提示抑止） |
| Song | videoId（11文字、曲の識別子）、title、artist、order、updatedAt（旧由来はnull可）、profiles（DAM/JOYSOUNDの任意キー）、pendingLegacy（割当て保留の旧設定・由来、必要時のみ） |
| SyncProfile | service（DAMまたはJOYSOUND）、savedPositionSec（有限の0以上またはnull）、offsetSec（有限）、threshold（有限0〜1）、durationMs（0以上の整数）、updatedAt（移行時null可） |
| Backup | appName、schemaVersion=1、exportedAt、library |
| SessionSnapshot | generation、videoId、service、profileKey、開始位置、しきい値、継続時間、設定revision。永続化しない |

プロフィールの識別は `(videoId, service)`。DAM/JOYSOUNDは最大各1件で、片方が未登録でもよい。曲名・アーティストは共有し、設定値は共有しない。未登録側で自動的に他方の位置を流用しない。選択機種を明示して保存し、削除は機種設定単位と曲全体を区別する設計案（N-07）。

位置は保存時にミリ秒整数へ丸めて秒値として扱い、0.05秒操作を50msの整数加減算で行う。旧値を50ms刻みに強制丸めしない。手動調整の分解能と実発音精度は別。

ID重複はプレビューに出し黙って消さない。JSON入力は実行せず、許可フィールドだけから新しいオブジェクトを構成する。機種・設定の型を検証し未知serviceは勝手にDAMに変換しない。

### 一元管理する暫定初期値（Q-13への提案）

以下は実測前の初期提案。`src/config/`の単一設定定義を正本とし、UI・検証・adapterへ注入する。テストは設定を差替え可能とする。保存スキーマ番号と50ms操作刻み等の確定仕様を、資源上限と混同しない。

| 項目 | 暫定値 | 理由・超過時 |
| --- | --- | --- |
| 曲数 / プロフィール数 | 1,000曲 / 最大2,000件 | 通常の練習リストを十分上回る。上限超過は追加前に説明し書込みしない |
| 曲名 / アーティスト | 各200 Unicodeコードポイント | 長い正式名を許容し、過大入力を制限。超過は切捨てず検証エラー |
| 新版保存JSON | UTF-8換算2MiB以下 | 1,000曲の通常値を想定。実容量は旧キーの保持やブラウザに左右され、2MiB保証ではない |
| 取込ファイル | 5MiB以下、最大1,000曲・各2プロフィール | JSON整形や由来情報の余裕。マージ後も曲数・2MiBを再検証し、一部だけ黙って取込まない |
| 補正 | -30〜+30秒、操作50ms | 秒単位の開始差を広く調整。大きなイントロ差は保存位置で合わせる。旧値超過は原値保持して解決を要求 |
| 新規検知設定 | threshold=0.08、調整0.005、durationMs=50 | 旧しきい値を比較基準とし短い雑音除去を試す。最適値の保証なし |
| 継続時間 | 0〜2,000ms、調整10ms | 0msの即時判定と長めの比較試験を両立。長い値では遅延を案内 |
| 有効観測の最大間隔 | 100ms | 描画停止を音の継続と誤認しない。端末負荷試験で再評価 |
| マイク許可待ち / API読込 / cue | 60秒 / 15秒 / 15秒 | 許可操作と回線に余裕。超過で待機せず、遅着資源を解放 |
| 検知待機期限 | armed移行から5分、期限1分前から残りを表示 | 曲開始待ちに余裕を持ち、放置取得を抑制。検知成立でこの期限を解除し、未検知の期限超過時は停止・明示再準備 |
| PLAYING確認 / 停止確認 | 10秒 / 3秒 | ハング検出の上限。精度±100msの合格判定には使わない。超過は停止/破棄を案内 |
| 診断ログ | 2,000件またはUTF-8換算1MiB、いずれかで古い順に破棄 | スマートフォンのメモリを抑制。欠落件数を表示。セッション要約を優先 |
| 音量UI更新 / 波形保持 | 最大10Hz / 常時録音なし | 描画負荷を抑え、検知頻度とは分離。実機計測の録音は同意した別手順 |

これらの値は曲数×最大文字数の全組合せ保存を保証しない。データ量と実ブラウザの空き容量を両方検査し、quota失敗時は旧/新の既存データを保持する。旧データの長文・範囲外値は移行保留にして原本を残す。上限を変える場合、超過済みデータを自動削除せず読み取り・退避可能にする。

| 保存候補 | 利点 | 弱点 | 判断案 |
| --- | --- | --- | --- |
| 単一キーlocalStorage | 少量データに簡単、1回setItemで全体置換 | 同期I/O、容量制限、複数タブの競合 | 初期推奨 |
| IndexedDB | トランザクション、大量データ | 非同期管理と移行が増える | 曲数増加・音声保存が要件化した時 |
| サーバーDB | 複数端末同期 | 認証、運用、プライバシー管理 | 初期対象外 |

新キー案は `karaokesync.library.v1`。旧キーは変更しない。検証済みJSONを1回setItemし、例外ならUIの保存済み状態を更新しない。改訂番号とstorageイベントで他タブ変更を検出し、黙った上書きを避け再読込を要求する。localStorageは複数タブ間の比較交換を保証しないため、初期版は単一タブ編集を案内。厳密な同時編集は別要件。

### 移行・復元

1. 新キーがない時だけ、旧4種のキーを読取り候補にする。song_list順を維持し、孤立キーも検出して復元候補として報告する。
2. 文字列savedSecを有限数に変換しnullは未保存として維持。threshold=0は有効。欠損値は旧既定値を候補として表示し、明示値の破損/範囲外は保留。原値を黙って置換しない。
3. 旧songInfo.serviceがDAM/JOYSOUNDならそのプロフィールだけに旧位置・補正・しきい値を割当てる。新規継続時間は旧挙動互換の0msを提案してプレビュー。もう一方は未登録とする。
4. 未指定/未知serviceはpendingLegacyに旧設定と由来を保持し、DAM/JOYSOUNDへの明示割当てを求める。両方へ自動複製しない。未解決ならその設定で検知を開始できない。既存と衝突した場合も同じプレビューへ回す。N-04で扱いを確認。
5. 移行プレビューと旧JSON退避を案内し、承認後に新キーへ一括保存。旧キー削除や自動再生をしない。旧データ保持は新版の全削除でも守る。
6. 新キー存在時は毎起動で旧データを再マージしない。再取込は明示操作。由来・内容指紋で同一の保留候補を増殖させない設計とする。新版全削除時の空データ保持は次項のRV-05に従う。
7. 旧バックアップ0.6、新schemaVersion=1を別パーサーで正規化。未知版は拒否。新規曲/未登録プロフィールは追加候補、重複はvideoId×service単位で個別選択。共通曲情報とpendingLegacyも差分を表示し、設定の選択で別機種や曲名を黙って上書きしない。既定は既存保持の案（N-05）。
8. 選択結果をメモリ上で全件検証し、曲数/サイズ/重複を検査して1回保存。失敗時は不変。成功後は選択機種を含めセッション状態を再構築し、自動再生・自動待機をしない。

originが変わると旧localStorageは読めない。同一originならキー移行、別origin/アプリなら旧画面からのJSON出力→新画面で取込が必要。旧画面が起動できない場合の救出手順を移行段階で準備する。公開先を未確認のまま自動移行可能と約束しない。

### 新版全削除後の再取込防止（レビュー改善案RV-05）

新キーをremoveItemする方式は採らず、`songs=[]`、`legacyImportPolicy=自動候補提示抑止`、更新revisionを持つ有効な空Libraryを同じキーへ1回保存する。曲データと抑止情報を別キーに分けない。これにより「新キーなし→旧データ移行候補」の分岐を誤って再実行しない。成功後も旧キー・旧バックアップは保持し、削除完了表示は保存成功後に限る。失敗なら元の新版Libraryを維持する。

明示的な「旧データを取り込む」は抑止状態でもプレビュー経由で利用可能。新バックアップのlibraryには可搬データだけを出力し、端末ローカルのlegacyImportPolicyを含めない案。復元でも取込元の値で端末の抑止方針を上書きしない。保存形式を読むときはこのフィールドの省略を許容し、承認前に書き込まない候補提示扱いとする。

ブラウザのサイトデータ全消去・別origin・キー破損では抑止履歴を復元できない。その場合も旧候補の検出までにとどめ、承認なしに新版へ書き込まない。キー破損時は初回と断定せず救出案内。旧曲が勝手に復活しないことと抑止情報の保持範囲をN-08で確認する。

## 8. エラーと診断

カテゴリはinput、permission、unsupported、player、audio、storage、timeout、cancelled。ユーザー表示は日本語の原因・現在の安全状態・次の操作、開発ログはコード・世代・状態・操作・経過時間を持つ。cancelledを障害成功率に混ぜない。

performance.nowによる単調時刻で、操作、取得開始/終了、CUED、armed、最初の超過観測、継続条件成立、play要求、PLAYING、停止要求/完了を記録。端末/OS/ブラウザ、profileKey、固定した位置・補正・継続時間、sampleRate、Context.state、入力設定を取得できる範囲で記録する。音声・連絡先・完全URLは既定で保存しない。曲IDやデバイスラベルも診断出力時に確認/匿名化する。ログは前節の上限で管理。

ログから分かるのはアプリ内の時間差。カラオケの実音開始とイヤホン発音との差は、別の物理計測が必要。Bluetooth遅延をPLAYINGだけで推定確定しない。

### 高精度同期と開始ばらつき

確定操作は50ms刻み、暫定目標は手動調整後の実音ずれ±100ms、努力目標は±50ms程度。再現試験では調整後のプロフィールを固定し、試行ごとの追い込み直しでばらつきを隠さない。

各試行で、外部の伴奏基準音時刻T0、最初の超過観測T1、検知成立T2、play要求T3、PLAYING受信T4、対応する動画音がイヤホンから聞こえた時刻T5を可能な範囲で取得。T0/T5は同じ外部計測時計、T1〜T4はアプリの単調時計とし、校正なしに両時計を減算しない。Worklet使用時もAudioContext時計との対応と誤差を記録する。

内部ではT2−T1、T3−T2、T4−T3とフレーム間隔を診断。外部では同じ音楽上の対応点について符号付きずれeを測り、平均、中央値、標準偏差、p95(|e|)、最大|e|、±100/50ms内比率、再生開始遅延のp95−p5を集計する。測定できない値は欠測とし、再生失敗を統計から黙って除外しない。

冷起動/繰返し、回線、広告/バッファリング、マイク保持/解放、機種、イヤホン、検知設定を分けて比較する。固定オフセットによる偏りと試行間のばらつきを分離する。成功率、許容外れ数、測定誤差を含む最終合格条件はN-01。平均のみ目標内でも製品合格としない。

## 9. テストとCodex運用

以下は完成時の構成であり段階1の一括導入要件ではない（レビュー改善案RV-01）。段階1は最小Vitest・状態管理・ログ、段階2は実adapterと実機成立性、段階3〜5で必要なPlaywright/CI/広い回帰を追加する。最初から必須なのは検知前play禁止、停止後の遅着処理無効化、1回要求、play直後pause、終了/拒否/期限時解放の基本テスト。

- Vitest: URL、50msの整数加減算、0/null/NaN/Infinity、しきい値＋継続時間（0ms、境界、途切れ、観測欠落）、DAM/JOYSOUND独立性、旧service割当て・保留、復元の機種別選択、検索順、reducer全遷移。
- 結合: 手動完了できるPromiseと模擬player/mic/storageで、停止後の取得、許可待ち連打、古いCUED/PLAYING、切替、復元失敗、重複検知を検証。
- UI: Testing Libraryで準備/停止/失敗表示と操作可否、アクセシブルなラベル。
- Playwright: 模擬外部APIで決定的な主要フロー。WebKitを優先し、Chromium/Firefoxは回帰補助。WebKit実行をiPhone実機合格と扱わず、Android対応も意味しない。
- 実YouTubeは小さな接続確認スイートに分離し、外部停止・動画変更を製品コード不具合と混同しない。
- 物理端末は停止とBluetoothの経路・実発音を検証。模擬音声で代替しない。

承認後のCI案はlockfileで依存復元→lint→typecheck→unit/integration→build→mock E2E。失敗時にtrace、画面、console、正規化ログを保存し、fixtureとテスト名で再現可能にする。Codexは再現テスト→最小実装→対象テスト→必須全検査→差分確認の順で反復する。テスト削除・期待値緩和・実機合格の捏造で通さない。3回同原因が続く等の停滞時は診断をまとめ、仕様判断/権限/実機操作が必要なら人へ戻す。自動push・公開・マージは運用に含めない。

## 10. 提供形態と実現可能性

以下はAPIの存在と設計上の比較であり、対象端末の合格結果ではない。

| 形態 | iOS | Android | 利点 / 課題 |
| --- | --- | --- | --- |
| Web | Safari系環境で権限・AudioContext・再生制限を検証。AudioSessionは能力検出 | Chrome等で入力選択・省電力・割込みを検証 | 最小の配布/自動テスト。Bluetooth出力と本体入力の同時固定は保証不可 |
| PWA | インストール状態で別途実測 | 単体表示・更新・省電力を実測 | 起動導線改善。権限や経路の制限を解消する仕組みではない |
| WebView＋native audio | AVAudioSessionで候補経路・割込みを扱い、WKWebViewの動画音声との共存を試験 | AudioRecord/AudioManagerとWebView再生の共存・権限を試験 | UI/domain再利用。JS bridge、音声所有権、ライフサイクルが増える |
| native UI/audio | AVAudioSession/音声入力で制御。ただしYouTubeは正規埋込等の別検証 | 音声APIと端末別経路、YouTubeの埋込を検証 | OSイベントを詳しく扱える。二OSのビルド・UI・実機試験の負担が最大 |

A2DP、HFP、LE Audioを一括りにしない。音楽出力とマイク利用で経路・音質が変化する可能性があり、OS版・機器・選んだ入力で異なる。AndroidのsetCommunicationDeviceは通信用途のAPIであり、YouTube音楽の出力固定を保証する手段ではない。iOSのpreferredInputも任意の入力と出力の組合せ保証ではない。

確定方針はiPhone向けWeb最小検証を先行。本体/イヤホンのマイクのどちらでも正常検知でき、Bluetooth出力と同期目標を満たせればよい。Androidは後段の検討とし、比較表は将来評価用。Webの制約で要件を満たせなければUI作り込み前にnative連携を検討する。PWAはBluetooth解決策として採用しない。バックグラウンド再生、音声抽出、プレイヤー非表示を解決手段にしない。

native化してもYouTube動画を任意のネイティブ音声エンジンで再生する設計にはしない。正規埋め込みとの共存を試す。iOSのビルド・署名・実機自動化にはmacOS/Xcode等の環境が別途必要で、現在のWindows環境だけで完結すると見積もらない。AndroidもSDK・エミュレーター・実機を追加する必要がある。両OSのネイティブ機能を採用する場合、共通化するのはdomainとデータ変換を中心にし、経路制御はOS別に実装する。
