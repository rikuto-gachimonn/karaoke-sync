# KaraokeSync 段階的な再実装計画

作成・更新日: 2026-10-18 / 状態: Q-01〜Q-13の決定を反映。今回は文書更新のみ。設計更新のレビューと実装開始承認が済むまでアプリ実装・依存導入・検証用アプリ作成を開始しない。

関連: [仕様](requirements.md)、[設計](architecture.md)、[未決定・検証一覧](open-questions.md)。この計画のテストは今後作るもので、今回合格済みではない。

## 共通の進行規則

- 現在の `feature/codex-karaokesync` で進める。既存HTML、main、tatusを設計作成では変更しない。将来の旧版整理も別途合意する。
- 各段階で要求ID、実装範囲、テスト、ログ、未解決事項を対応付けてレビュー可能にする。
- 必須の失敗を残したまま次段階の機能を重ねない。実機未検証は未検証と記録。
- 0.05秒操作刻みは確定。調整後±0.1秒は暫定目標、±0.05秒程度は努力目標。精度・再生開始安定性の最終判定は実測で決める（N-01）。資源上限はarchitecture.mdの暫定初期値を正本とする。
- iPhone＋Bluetoothイヤホンを先行し、本体/イヤホンのどちらのマイクでも正常検知できればよい。Androidは初期ゲートに含めない。無料の開発・テスト環境を優先する。
- push、マージ、公開はこの計画の自動運用には含めない。

## 段階0: 設計のレビューと承認

**対象**: 決定反映後の4文書レビュー、追加判断N-01〜N-09と暫定値の確認、iPhone・イヤホン・検証担当の選定。後段に必要な詳細判断は対応段階まで保留でき、段階2の成立性確認を不要に遅らせない。Q-01〜Q-13を最初から問い直さない。コードは作らない。

**完了条件**: 確定方針と詳細案を区別し、検証条件・測定方法・保留項目のゲートを合意。マイク保持の採否は段階2へ残す。Q-13への上限・期限提案をレビューする。

**自動確認**: 文書リンク、要求ID、計画と未決定一覧の整合確認。アプリ自動テストは未導入。

**実機確認**: この段階では不要。実機試験は承認後の段階2で行う。

**次へ進む判断**: ユーザーが設計と実装開始を明示承認。Bluetooth成立はまだ確定しない。

## 段階1: テスト可能な最小基盤

**実装対象（レビュー改善案RV-01）**: 最小のTypeScript＋React＋Vite、Vitest、状態管理、Player/AudioInput/Detectorの必要最小限の窓口・模擬入力、config、時刻付きローカル診断だけ。画面は動画ID・開始位置・検知設定の入力、準備/一時停止/再生/すべて停止と状態表示に限定する。Repository実装、曲管理画面、将来照合機能、広範なPlaywright、CIは段階1の対象外。Q-11のPlaywright採用を撤回せず導入時期を後ろへ移す。

**完了条件**: clean環境で同じコマンドが実行でき、外部APIなしでR-01/R-05のテストが安定。実アダプターなしでも操作意図と遷移を検証できる。

**自動テスト**: Vitestで検知前play禁止、停止後の遅着取得/イベント無効化、再生要求1回、play直後pauseの競合、終了/拒否/期限超過時の解放を最初から検査。状態遷移と必要な位置/検知計算だけを対象にし、typecheck/buildも実行。網羅的UIテストや全データモデルの試験は後段へ回す。

**実機確認**: HTTPSの表示、狭い画面で停止ボタンが操作可能。音声の成立判定はまだしない。

**判断基準**: 上記の基本安全テストとtypecheck/buildが通り、遅延イベントをログで追えたら直ちに段階2へ進む。Playwright trace、CI、完成した曲管理をゲートにしない。確定スタックは維持する。

## 段階2: Bluetoothと再生開始の早期検証

**実装対象**: 最小YouTube・マイクadapter、CUED待ち、AudioContext.resume、停止、音量＋継続時間（0msを含む）、検知終了と資源解放の分離、診断時刻・試行要約。装飾・完全な曲管理の前にV-01〜V-05を試す。

**完了条件**: iPhone/イヤホンごとの入力/出力、マイク保持の効果、超過開始→検知成立→要求→PLAYINGと外部の実発音を分離して記録。補正固定の反復試行で偏り・標準偏差・p95絶対ずれ・目標内比率・開始遅延の分布・失敗率を出せる。広告/バッファリングも別条件とし、予備再生に依存しない。

**自動テスト**: 遅着stream解放、prepare失敗、CUED前検知拒否、PLAYING期限超過、onAutoplayBlocked、停止後のPLAYING、API未読込、マイク拒否、継続0ms/正値/中断、試行統計・欠測・失敗の集計、時計の混同防止。

**実機確認**: iPhone Safari＋Bluetoothを主対象に、本体/有線を比較基準として可能な範囲で測る。入力は本体/イヤホンを記録し正常検知を確認。検知前発音、すべて停止、経路変化、継続時間0ms/50ms等、冷起動/繰返し、±0.1秒/±0.05秒目標とばらつきを評価。回数・物理測定はV-04参照。Androidは不要。

V-05の成立性を最初に確認する。初回操作/手動再生経験、0・5・30・120・240秒待機（探索用）、Bluetoothの事前接続/準備後接続/再接続を区別する。切断でセッションが無効になった試行は再準備し、無効セッションを再開しない。検知後のplayVideo、ブロック、PLAYING、実発音を記録し、手動操作は比較対照とする。網羅的な精度測定の前に、基本の検知→再生が成立するか判断する。

**判断基準**: 暫定目標との差と安定性を可視化し、N-01の最終基準をユーザーと決定するまで製品合格としない。Q-03を満たし改善見込みがあればWeb継続。満たさなければ原因を検知/プレイヤー/経路に分け、rAF/Workletを比較。Web制約が主因ならnative連携試験を別途判断する。マイク保持方針Q-06を実測から選ぶ。PWAだけで改善するとは判断しない。

自動再生の分類と分岐はarchitecture.md「自動再生の成立性」に従う。実装/配信設定不備は修正して再試験。通常の初期準備と待機後に安定して自動再生できればWeb継続候補。毎回検知後のタップが必要、または隠れた先行再生に依存する場合は中心要件未達とし、後段の画面完成を止めてユーザー判断へ戻す。native連携は同じYouTube条件を最小試験し、必ず解決するとは仮定しない。

## 段階3: セッション制御の完成

**実装対象**: R-01〜R-11、手動再生と待機の排他、50ms位置/補正調整、一時停止→続きから再生、検知条件、資源寿命、背景移行時の安全解除・切断・割込み対応、全エラー表示。背景再生機能は作らない。

**完了条件**: 準備/待機/再生中どこでも停止可能。停止後に自動再開せず、現在世代の検知1回だけがplayを起こす。マイク保持の表示と解放が承認方針に一致。

**自動テスト**: 段階1の安全テストを拡充。開始連打、停止→即再開始、Promise完了順、曲/機種切替、古いrAF・イベント、pause失敗、一時停止後seek/armなし、play直後pause→遅着PLAYING→pause再発行、新たな明示再生との識別。ENDED→マイク解放と再武装なし、拒否・待機期限超過・遅着stream解放、解放失敗表示。模擬波形の境界・中断も検査。反復で必要な少数のPlaywright smokeから導入し、CIはテストコマンドが安定してから段階3〜5で整備する。

**実機確認**: 許可ダイアログ中の停止、ホーム画面移行、画面ロック、着信、イヤホン切断、復帰、マイク表示消灯。端末で検出できない事象は制約として記録。

**判断基準**: 停止安全性の必須項目に失敗がない。未対応環境は明示的に検知利用不可にできる。

## 段階4: 曲管理・移行・バックアップ

**実装対象**: 共通曲情報とDAM/JOYSOUND別プロフィール、一覧・検索・並替、旧キー/JSON0.6の機種割当て・保留、新schemaVersion=1、復元プレビュー、新規追加候補と重複設定の個別選択、1回保存、設定/曲削除。旧キー・原本は削除しない。

**完了条件**: 既存の能力を引継ぎ、旧データを改変せず移行できる。失敗時は既存データを維持。選択中設定を復元後に再構築。別originの移行手順も用意。

**自動テスト**: DAM保存がJOYSOUNDを変えない、選択機種のsnapshot固定、旧指定機種のみ移行、未指定/未知service保留、移行duration=0ms、未登録側に流用しない、片側だけ上書き、曲情報競合、保留候補の再取込重複防止。0/null/文字列秒、破損、孤立キー、未知版、曲数/容量上限、全件不変、往復、他タブ検出。旧キー不変を検査し、実データで削除試験をしない。

RV-05の削除テストを追加する。新版全削除→再起動でも旧データを自動取込せず、空の新版Libraryと抑止情報を同時保存する。保存失敗は削除完了と表示せず、旧キーは不変。明示再取込ではプレビューを経る。ブラウザの全サイトデータ消去による抑止情報喪失も試験し、新キー不在時でも自動書込みをしないことを確認する。

**実機確認**: iPhoneのJSON保存と選択、再起動後保持、機種切替、旧公開先→新公開先の受渡し。旧データを事前退避。Androidは後段。

**判断基準**: 有効旧データの各項目と順序を保ち、不正データは黙って捨てず報告。移行を再実行して二重登録しない。

## 段階5: 利用体験と受入試験

**実装対象**: 操作画面の完成、案内、状態説明、診断出力、レスポンシブ、アクセシビリティ、必要なら検知パラメータ調整。

**完了条件**: 初回調整から通常利用・停止・再準備・バックアップまで一連の操作が可能。対象環境と非保証事項を利用者向けに説明できる。

**自動テスト**: 主要フローのmock E2E、各ブラウザ、狭幅表示、ラベル・フォーカス、保存再読込、エラー復旧。実YouTube接続試験は別枠。

**実機確認**: iPhone＋Bluetoothで実店舗または同等の伴奏音量・雑音を使用し、歌・会話・拍手と伴奏開始を比較。DAM/JOYSOUND別の固定設定で再現試験し、開始ばらつきと途中のずれを別記。途中バッファリングも記録。

**判断基準**: 承認した対応表で開始ずれ、成功率、誤検知率、停止が合格。未合格項目をテスト変更で隠さず、検知改善/提供形態/範囲のどれを見直すか判断する。

## 段階6: 配布形態の確定と運用

**実装対象**: Web配布手順、必要性が承認された場合のPWAまたはnative連携。PWAの更新通知・キャッシュ互換、nativeのbridge世代・権限・ライフサイクルを追加設計する。

**完了条件**: 配布・更新・ロールバック・データ保護手順、対応表、未解決制約が揃う。YouTube埋込条件を再確認。

**自動テスト**: 本番ビルドsmoke、旧データ→更新、更新中の再生禁止、キャッシュ不整合。native採用ならOSビルドとbridge契約試験。

**実機確認**: インストール形態ごとの再生・入力経路、更新後再起動、移行・復旧。WebとPWA/WebViewを同じ結果とみなさない。

**判断基準**: 選んだ配布形態で段階5の必須試験を再合格。公開は別途ユーザー承認を得て行う。

Android、自動位置合わせ、イヤホン別追加プロフィールは将来の別計画とする。自動位置合わせは参照素材と手法の成立性を先に検証し、IFrame APIからの直接音声取得を前提に実装着手しない。

## AIが反復する開発サイクル

1. 要求IDと失敗シナリオを選び、再現するテスト/fixtureを先に作る。
2. 責務を越えない最小の変更を行う。
3. 対象テストを実行し、失敗時に例外・状態ログ・traceを読む。
4. 同じ再現条件で修正し、成功後に必須検査一式を実行。
5. diff、保存形式、資源解放、未検証の実機条件を確認し、結果を報告。

想定コマンド契約は `npm ci`、`npm run lint`、`npm run typecheck`、`npm run test:unit`、`npm run test:integration`、`npm run build`、`npm run test:e2e`。現時点では未定義。導入後に名前を固定する。

これは最終的なコマンド集合。段階1では依存復元・必要なVitest・typecheck/buildのみを最小契約とし、lintの拡充、結合試験専用コマンド、Playwright、CIは必要になった段階で追加する。

外部YouTube不調はmock契約試験と分け、端末操作・仕様選択が必要ならAIはその根拠と必要な操作を報告する。失敗テストの削除、無条件skip、同期目標の引下げ、自動pushで完了扱いにしない。
