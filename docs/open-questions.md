## 3. 実機試験プロトコル案

テスト表には端末型番、OS版、ブラウザ版、通常/PWA/WebView、イヤホン型番、A2DP/HFP/LE Audio等の分かる範囲、入力、出力、権限状態、回線、動画、DAM/JOYSOUND、保存秒・補正、しきい値、継続時間、マイク保持/解放、サンプルレート、分析窓、フレーム間隔、試行番号を記録する。不明な値は推定で埋めない。

最初はiPhone Safari＋Bluetoothを必須とし、本体出力・有線を可能な範囲で比較基準にする。所有機器をN-01で指定し、Androidは後段。1機種の結果を全iPhone対応としない。PWA/nativeは採用時に別条件として再試験する。

V-04は自作の基準音・YouTubeに正規埋込可能な基準動画を用い、伴奏基準音とイヤホン発音を同期した二経路録音/外部計測器で測る。配信/計測準備は今回行わない。動画の基準音が開始位置から何秒後に来るかを既知にして、期待発音時刻との差e（遅れを正）を求める。基準動画の開始試験と、本人歌唱の音楽上の対応点での利用評価を分ける。

アプリのT1〜T4（超過観測、成立、要求、PLAYING）と外部計測のT0/T5（伴奏基準、イヤホン発音）は別時計。校正なしに横断減算しない。外部計測の不確かさを記録し、50msを評価できる時間分解能・誤差が得られない場合は努力目標の数値合格を出さない。イヤホン音を測れない場合もユーザー評価扱いとする。

仮の試行計画は主要条件ごと20回以上。キャリブレーション用試行で0.05秒刻みの補正を決めた後、評価試行では同じ設定を固定し、試行ごとに補正し直さない。平均、中央値、標準偏差、p95(|e|)、最大|e|、±100/50ms内比率、開始遅延のp95−p5、未検知・誤検知・再生失敗率と分母を記録。欠測・広告・バッファリングは別記し黙って除外しない。

20回は探索用で、裾の確率を十分保証しない。最終回数・許容外れ率はN-01で実測から決める。平均が±100ms内というだけでは合格としない。許可済みの成功例だけを集めず、冷起動・初回権限・長めの待機も分ける。物理録音の同意・保管方針は開始前に確認する。

## 4. 現在の証拠と不足

- 確認済み: コード、README、全開発コミットの一覧、主要なVer.0.7差分。現在の閾値方式・保存形式・マイク保持をソースで確認。
- 既存調査で再現: 不正ホスト/文中11文字の受入れ、しきい値0の復元が0.08になる問題。実機障害の再現ではない。
- 決定済み: iPhone Web先行、入力マイク不問、50ms操作、DAM/JOYSOUND独立、検知＋継続時間、旧データ保持、スタック等。精度の暫定目標はある。
- 不足: 実機結果、最終精度・安定性基準、Bluetooth経路実測、マイク保持方針、公開URL、実データ量、対象OS下限、詳細設計レビューと実装開始承認。
- 公式資料はAPIの能力・制約の根拠。KaraokeSyncでの成立証明ではない。[設計書](architecture.md)末尾の公式資料一覧を参照。
