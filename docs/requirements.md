## 2. 目的・範囲

DAM・JOYSOUND等の採点を使用しながら、スマートフォンとイヤホンで本人歌唱を聴いて練習する。周囲の伴奏開始をマイクで検知し、ユーザーが決めた動画位置から再生する。

確定方針は、iPhone向けWeb版で最小の技術検証を先行し、画面をつけた前面利用とすること。Bluetoothイヤホンを最優先とし、入力は本体・イヤホンのどちらでも伴奏を正常検知できればよい。Androidは後から検討する。Webで要件を満たせない場合はネイティブ連携を検討する。バックグラウンド対応は初期必須にしない。

初期対象は埋め込み可能なYouTube動画、手動調整・保存、一度の開始検知。カラオケ機器への接続や採点取得、歌声認識、演奏中の連続自動同期、音声抽出・保存、クラウド同期は初期対象外という設計案を維持する。

「同期」は開始位置を合わせることを指す。動画と伴奏のテンポ・編集・間奏が違えば、全曲の同期は保証できない。手動調整は0.05秒刻みとする（確定）。調整後の実発音のずれ±0.1秒以内を暫定目標とし、可能なら±0.05秒程度を目指す。精度と開始の安定性を重視し、実測から最終基準を決める。平均だけで合格にせず、開始ばらつき・失敗率を測る。集計方法・合格率はN-01。

## 4. 画面と操作

単一画面を基本とし、上から「選曲」「可視動画・位置調整」「検知準備と大きな停止ボタン」「曲情報」「データ管理・診断」を配置する案。補助設定は折りたたみ可能とする。viewport、狭い画面での折返し、ボタンの日本語ラベル、キーボード操作、状態の文字表示に対応する。

### 初回の位置合わせ

1. イヤホンを接続し、出力をユーザーが確認する。アプリが判定できない経路は「不明」と表示。
2. URL/IDから動画を選択。選択だけでは再生しない。
3. ユーザーの明示的な手動再生で位置を調整し、「同期位置を保存」。これはカラオケの基準となる音に対応する動画位置であると案内する。
4. DAM/JOYSOUNDを選び、曲情報、同期位置、しきい値、継続時間、補正を保存する。基準音を選ぶ具体的な案内はN-02。機種変更で他方の設定を上書きしない。

### 通常利用

1. 保存曲とDAM/JOYSOUNDを選ぶ。動画は停止したまま該当プロフィールを読み込む。未設定なら調整・保存を案内し、他機種の値を黙って流用しない。
2. 「検知を準備」を押す。マイク許可と動画準備が終わるまで「準備中」。
3. 「検知待機中」になってからカラオケを開始する。準備中の音を後から遡ってトリガーにしない。
4. 条件成立で一度だけ再生要求。「音を検知」「再生を要求」「動画再生中」を区別する。
5. 必要なら位置を微調整。次の演奏は明示的に再準備する。
6. 「すべて停止」で検知と再生を止める。マイクも解放する。

一時停止は動画だけを一時停止し、「再生」で続きから再開する。検知は自動再開しない。マイクの保持/解放は一時停止操作から独立した資源方針に従う（Q-06は未確定）。「すべて停止」は動画・検知・マイクを終了する。停止後の位置扱いはN-03。

手動再生は検知前再生禁止の例外となる明示操作であり、検知待機を解除してから行う設計案。YouTube標準操作部の意図をAPIから完全識別できるとは仮定せず、待機中の想定外PLAYINGは待機解除・pauseとする案をN-03に残す。

## 5. 検知・再生・停止の要求

R-01/R-04/R-05/R-10/R-11は確定方針を具体化。その他の詳細手順はその実現のための設計案で、対応端末の実証は別途必要。

| ID | 要求・受入条件 |
| --- | --- |
| R-01 | 選曲、起動、復元、検知準備ではplayを発行しない。自動playの発行は有効な待機セッションの検知成立後1回だけ |
| R-02 | 動画準備・マイク取得・AudioContext稼働を確認した場合だけ待機状態にする。cue完了はバッファ完了と表示しない |
| R-03 | 音量しきい値と継続時間を組み合わせる。0msは最初の有効な超過判定で成立する。比較演算・連続性・初期値は試験する。デバイスの音声補正無効化は要求として扱い、適用値を記録 |
| R-04 | 検知成立の瞬間に待機を解除し、再検知を防止。動画PLAYINGを受けるまで「再生中」としない |
| R-05 | すべて停止は即時にセッションを無効化。遅延した許可結果・タイマー・旧イベントから再生しない。遅着したstreamは直ちに解放 |
| R-06 | 停止は繰返し可能。停止ボタンは準備中も有効。pause/資源解放の結果を確認し、失敗時は未完了を表示。外部プレイヤーの停止まで物理的遅延ゼロとは保証しない |
| R-07 | 曲切替、選択曲削除、全削除は先に待機解除・再生停止・資源解放。停止を確認できない場合は切替を完了扱いにしない |
| R-08 | 再生ブロック時は再生成功とせず、停止した状態からユーザーの再生操作を案内。自動再試行で予期しない発音を起こさない |
| R-09 | バックグラウンド移行・入力切断・割込みを検出できたら待機解除。復帰時に自動再武装しない。背景再生対応は別途判断 |
| R-10 | 一時停止は動画のみ。再生で現在位置から再開し、seek/prepareや音声検知の自動再開を行わない |
| R-11 | DAM/JOYSOUNDそれぞれの同期位置・補正・しきい値・継続時間を独立保存する。選択機種をセッションに固定する |

現在はR-02のCUED待ち、R-05の世代管理、R-07の一括停止、R-08の専用表示がない。AudioContext.resumeもない。検知失敗後の資源解放が不十分。

### マイク保持とBluetooth

現状は検知成功後もマイクが稼働する。新仕様では検知処理終了とマイク解放を分離する（確定）。検知後に保持するか解放するかはBluetooth実機検証V-02で決める（未確定）。保持中は検知終了・マイク使用中を区別して表示し、すべて停止・離脱時は解放する。

必須なのはiPhone＋Bluetoothイヤホン出力で伴奏を正常に検知すること。本体マイク・イヤホンマイクのどちらも許容し、本体マイクへの固定を合格条件にしない。出力の安定性と聞きやすさは実測・利用評価する。Webで不明な入出力経路を断定しない。

## 6. 位置調整と保存

開始位置案は既存と同じ `max(0, savedPositionSec + offsetSec)`。正の補正は動画の先の位置から始めることで、再生要求を先送りする時間ではない。動画の長さが既知なら範囲超過を通知して再調整させる。NaN、Infinity、負の保存位置を拒否する。操作刻みと実際のYouTubeシーク精度は区別する。

位置・補正の調整単位は0.05秒。繰返し操作の浮動小数誤差を避ける設計とし、表示の細かさを実精度と混同しない。固定の遅延は手動補正で調整し得るが、試行間のばらつきは固定補正では解消しない。

将来の自動位置合わせを初期設計で考慮する（確定）。提案位置を手動保存と同じ検証経路へ渡す拡張点を設け、初期版では実装しない。YouTube音声をIFrame APIから直接取得できると仮定せず、入力素材・照合手法・精度の実現可能性はN-06で別途検証する。

現状の保存キー: `song_list`（ID配列）、`sync_<id>`（秒の文字列）、`song_info_<id>`（title/artist/service）、`detect_settings_<id>`（offset/threshold）。旧版は機種別設定1組のみ。新版は動画ごとの共通曲情報と、DAM/JOYSOUNDをキーにした独立プロフィールを持つ。各プロフィールに同期位置・補正・しきい値・継続時間を保存する。

移行時、旧serviceが明確ならその機種にだけ旧設定を割当て、他方にはコピーしない。未指定/不明なら移行保留として原値を保持し、プレビューでユーザーに割当て先を選んでもらう案。新しい継続時間は旧動作を維持する0msを移行候補とし、変更が必要なら明示する。N-04で詳細を確認する。

新しい順は現状では最後の保存操作順。移行時に架空の作成日時を生成せず順序を保持する。永続化に失敗したら「保存済み」にせず、未保存を表示する。

## 7. バックアップ・復元

現状のJSONは `appName: "Karaoke Sync"`、`backupVersion: "0.6"`、`exportedAt`、`songs[]`。各曲はvideoId、savedSec、songInfo、detectSettings。savedSecは文字列またはnull。songsが配列であるかとID以外の検証は弱く、途中書込み失敗や選択中設定の陳腐化が起こり得る。

新仕様と移行設計案:

- 旧形式を読み込める。新形式はschemaVersionを付け、DAM/JOYSOUNDのプロフィールを含める。旧版への新形式書戻し互換は追加判断N-05。
- ファイル全体の構文・サイズ・件数・型・数値を先に検証し、追加/競合/不正件数をプレビューする。
- 新規曲・既存曲の未登録プロフィールは追加候補とし、重複する設定は曲×機種ごとに個別の上書き可否を選べる。プレビュー確定前に書き込まない（確定）。既存優先を選択初期値とする案、共通曲情報の競合粒度はN-05。
- 1回の保存で全件を反映し、失敗時に一部だけ復元済みにしない。未知の将来版は拒否し原本を保持。
- 実行前に待機・再生を停止し、成功後に一覧と選択中の状態を再構築する。失敗時は既存データを維持。
- 全削除は対象と取り消せないことを確認し、新版の対象データだけ削除。移行・復元・新版の全削除で旧キーや旧バックアップを削除しない（確定）。

上限値は設計書「一元管理する暫定初期値」を正本とする。合理的な値を提案済みだが実測前であり、ブラウザ容量の保証ではない。

## 10. 外部制約の根拠

2026-10-18確認。端末での実証とは別。

- [YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference): cue、CUED、PLAYING、onAutoplayBlocked、エラー153等。cueは動画バッファ完了の保証ではない。
- [YouTube必須機能](https://developers.google.com/youtube/terms/required-minimum-functionality): 可視プレイヤーと正規の埋め込みを前提に、公開前にも要件を確認する。
- [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia): secure contextと権限が必要。
- [AudioSession](https://developer.mozilla.org/en-US/docs/Web/API/AudioSession): 実験的API。存在だけでBluetooth経路を保証しない。
