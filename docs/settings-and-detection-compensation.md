# 設定保存・一括適用と検知継続時間の補正

## 保存・流用

音声検知欄の既存保存操作を「この設定を保存」に改称した。選択中の曲/手入力動画・DAM/JOYSOUND/HOME・歌声/伴奏の同じv4保存枠へ、画面入力と既存のモード別設定を保存する。他モード・他機種を変更しない。保存結果を通知する。

一括適用も既存の計画→確認→単一キーコミットを利用する。

- A（初期選択）: しきい値と継続時間だけ。自動補正ON/OFF、各曲の位置・補正等は保持する。既に自動補正ONの曲は、継続時間変更に伴って実効位置も連動する。
- B: Aに加え、選択モードの基準開始位置、旧オフセット、主調整、検知継続時間の自動補正ON/OFF、再生方式、比較補正（A/B）、安定化待機、事前シークを明示的な許可項目としてコピーする。
- Bでも曲情報・動画ID、他モードの位置、期限、マイク保持設定、補正採用履歴、未知のモード枠・旧アーカイブはコピー/削除しない。歌声用の基準位置は歌声用フィールドへ、伴奏用は登録位置へコピーする。
- 既存の登録曲・保存済み機種・保存済みモードだけが対象。手入力の保存設定への従来のフォールバックは登録曲についてだけ使用する。未登録の組み合わせは作らない。
- 確認欄でモード・曲数・全設定数・DAM/JOYSOUND/HOME別件数・上書き値を表示し、Bでは曲ごとの歌い出し/正負補正が失われることを警告する。取消は書き込まない。
- 曲リストとフォールバック設定の変更を確認し、曲リストの既存の競合検出と一回のlocalStorage書込みを通す。容量不足などで書込みが失敗した場合はメモリも更新しない。複数キーを順次更新する方法は使わない。

## 自動補正の計算と移行

`SyncInput.autoCompensateDetectionDuration?: boolean`をv4内に追加した。

- 新規の曲・機種・モード設定はtrue（ON）。既存曲に未保存のモードを新しく作る場合もON。
- 既存v1〜v4および旧バックアップでプロパティがない場合はOFF。読込時に保存値やキーを書き換えない。明示的にONへ変更/保存、またはBを確認して適用した場合だけ新しい補正を使う。
- ON/OFFは他の入力と一緒にモード別保存・バックアップ/復元する。v4の形式名・バージョン・キーを維持し、旧形式の入力も受け付ける。

歌声/伴奏とも同じ`playbackPlan()`を使い、検知継続時間Dを一度だけ加算する（旧cue/manualの内部互換経路へは加算しない）。

```
D = ONなら設定durationMs、それ以外は0
U = 基準位置 + 旧オフセット + 比較位置補正B + 主調整 + D
raw = U + 安定化待機S
要求開始位置 = clamp(raw / 1000, 0, 動画長)
検知成立後の待機 = 比較待機A + S + max(0, -raw)
```

内部の計算は整数ms。基準30秒・200ms・他の補正なしなら30.20秒、100/300/500msは30.10/30.30/30.50秒。Dをもう一度待機することはない。基準保存値自体へDを加えない。正負の既存補正とSの意味は維持し、残る負位置は従来どおり待機へ変換する。動画長が分かるcontrollerのシーク時に上限を制限する。

検知後の通常シークと検知前の事前シークの両方が同じplanを読む。事前シークした位置が停止中に維持されていれば検知後に再シークしない。旧伴奏/legacyの直接再生経路も、自動補正ONの場合は共通の範囲制限付きseek→playを通す。OFFの旧動作は維持する。UIにON/OFF・設定時間による加算量・動画長制限前の実効開始候補を表示する。

## リアルタイム補正・次回保存

細かな±0.05/0.1/1秒を維持し、別行に±5秒を追加した。既存の`adjustLive()`が現在のAPI位置へ加算し、0〜動画長へ制限してseekだけを要求する。許可上限を1秒から5秒に拡張し、範囲内の実際の要求差分だけを履歴へ記録する。表示時刻は既存の読取りで追従する。

次回推奨値は既存のresultId/採用合計で差分のみを主調整へ加えるため、Dを含めて再保存しない。「今合ってる」はAPI位置から主調整以外の開始項（D・Sを含む）を差し引いて主調整を保存する。現在セッションのリアルタイム結果がある場合は、その時点の合計を採用済みにする。同じ結果の「今回の調整を次回用に保存」がさらに加算されない。別セッションの結果は採用済みにしない。補間表示は保存に使わない。

## 過去実装の調査

- React導入コミット`f452a77f8285b315a7a2acec3d5fa23256ef5784`と最新main `4ac60724fc0dac862835a6c7494f0655534ab383`の`src/domain/sync.ts`を確認。Dは検知条件であり、開始位置の自動加算はなかった。確認した当該ファイルの履歴にも削除の形跡はなかった。
- 同導入コミットの`docs/stabilization-and-recommendations.md`は「200msの検知継続時間は独立した判定条件として維持し、補正へ自動加算しない」と明記。`startAdjustmentMs`は手動主調整、`stabilizationWaitMs`は検知成立後の予定待機の補正で、Dの自動補正ではない。
- 旧HTMLのVer.0.7コミット`7a49ad680a99edca62ec27d0350940690234e7a9`と現行保存版も確認。しきい値を超えた時に準備位置からplayする実装で、継続時間補正の復旧根拠は見つからなかった。
- したがって確認できたmainの履歴では「削除機能の復旧」ではなく、今回明示的に追加した選択可能な補正。未確認のブランチや未公開の過去実装まで存在しなかったとは断定しない。

共通検知器は最初のしきい値以上の観測から、観測時刻差が設定D以上となったサンプルで成立する。実マイクはrequestAnimationFrameごとにRMSを取得するため、フレーム間隔・入力バッファ・境界観測の遅れで実際の経過はDと一致しない。サンプル欠落やしきい値未満は従来のリセット条件を使う。今回は設定Dだけの補正であり、実測の音声開始・YouTube API要求後・Bluetooth発音の遅延や精度を保証しない。検知器・マイク/出力経路は変更していない。
