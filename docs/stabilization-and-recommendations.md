# 開始待機の比較・次回推奨値（2026-10-19）

## 対象と調査結果

feature/codex-karaokesyncのReact通常アプリを改修した。既存のliveAdjustmentMs、TriggerTrial、性能時計の診断ログ、曲・環境別保存を再利用した。旧HTML、README、tatus、既存ブラウザデータ、検証ページ①〜⑦は変更していない。外部サービス・依存パッケージ・通信先を追加せず、push・マージ・デプロイも行っていない。

改修前も累積補正と再生中の明示保存はあったが、停止後の採用・永続的な試行別結果・推奨表示は不足していた。検知後にseekが発生しており、事前位置決めを比較する余地があった。現時点では実発音のばらつきが減ったとは確認していない。

変更前のsrc/tests/docsは .local-https/recovery-before-stabilization-20261019 にコピーした。既存の未コミット変更は保持した。

## 位置と時刻の設計

すべての補正は整数msで計算する。保存した基準位置は書き換えない。

```
R = 選択トリガーのYouTube基準位置 + 旧オフセット + 有効B補正 + 主調整
S = 新しい安定化待機（初期値0、比較用0〜60000ms）
A = 従来の比較A待機（既存データの意味を維持）
開始候補 = max(0, R + S)
負位置の追加待機 = max(0, -(R + S))
総待機 = A + S + 負位置の追加待機
```

| 基準 | 主調整 | S | A | 総待機 | 動画開始候補 |
|---|---:|---:|---:|---:|---:|
| 15秒 | 0ms | 500ms | 0ms | 500ms | 15.5秒 |
| 0秒 | -1000ms | 500ms | 0ms | 1000ms | 0秒 |
| 0秒 | -1000ms | 1500ms | 0ms | 1500ms | 0.5秒 |
| 15秒 | 0ms | 500ms | 500ms | 1000ms | 15.5秒 |

既存Aは位置を進めない比較実験用の待機として残す。Sとは役割が異なる。Sを指定しない旧データは従来どおりS=0で計算する。

待機の起点は検知成立／手動開始の性能時計時刻。処理に使った時間を差し引いて残りの待機を予約する。予定要求時刻と実要求時刻の差も記録する。ただしブラウザのタイマー遅れ・再生要求後の遅延・Bluetooth出力遅延を自動推定して位置へ足すことはしない。S分の位置補正は既知の予定待機に対する補正であり、実発音時刻の補償を保証しない。

200msの検知継続時間は独立した判定条件として維持し、補正へ自動加算しない。開始位置は最終的に動画長へ制限する。待機に相当する冒頭の歌唱が飛ぶ場合や、動画末尾へ達する場合がある。

## 事前シークの比較

「開発者向け設定」に安定化待機と事前シークの比較設定を追加した。**初期値は0ms・事前シーク無効**。固定待機の効果を断定せず、既定の再生方式を勝手に変更しない。

事前シークを有効にした場合だけ、公式可視プレイヤーの手動事前再生→自動一時停止→マイク準備の後、検知を開始する前に開始候補へseekする。50ms間隔で2回、PAUSEDと目標±100ms以内のAPI位置を確認する。2.5秒で確認できなければ終了する。100msの確認許容幅は実際の同期精度保証ではない。

停止時は確認タイマーと取得を取り消し、遅着結果から検知や再生を始めない。PLAYINGが観測された場合は既存の安全制御で停止する。準備中にplayVideoを要求することはなく、隠れた予備再生も行わない。

検知後もPAUSEDと現在位置を再確認し、事前位置が維持されていればseekの再要求を省く。位置がずれていれば従来のseekへ戻る。事前シーク自体がiPhoneで安定するかは未検証。

## リアルタイム結果と推奨値

- 試行ごとに開始時設定、動画ID、環境、トリガー、マイク方針を固定して記録する。
- 各シークの時刻・要求量・範囲制限後の要求量・前後のAPI位置候補を記録する。個別操作は直近500件、累積値はその前の操作も含めて保持する。
- 今回の累積補正は次のセッション開始時に0へ戻す。過去の試行は混ぜない。
- 結果概要は新しい専用キー karaokesync.app.live-results.v1 に最大30件保持する。曲設定・旧キーへは自動反映しない。入力形式不正・保存失敗・別タブ更新時は元データを上書きせず通知する。
- 推奨値は現在の保存済み曲／環境設定を基準とする。設定未保存なら試行開始時設定を用いる。今回の操作合計から既に採用した分を引いた差分だけを主調整へ加える。
- S、A、200msの継続時間、推定できない発音遅延はリアルタイム操作量へ加算しない。
- 推奨値は同期調整欄の直下に表示する。「推奨値を適用・保存」でのみ確定する。「今回は変更しない」は結果側へ辞退を記録するだけで曲設定を変えない。追加操作で合計が変われば新しい差分を提案できる。
- 既存の「今回の調整を次回用に保存」も同じ採用処理へ接続し、独立した二重保存処理を廃止した。停止後も利用できる。
- 保存した結果IDと採用済み合計をliveAppliedという任意フィールドへ入れ、曲設定と同じ書込で保存する。再保存・再読込・バックアップ復元で同じ補正を再加算しない。採用後に追加操作した場合は新しい差分だけを反映する。
- 保存失敗時は画面設定を採用済みにせず、次回の再試行でも補正を失わない。未保存編集と候補の基準が異なる場合は置換確認を行う。

例：基準15秒・既存主調整0ms、操作合計+300msなら、YouTube基準15秒はそのまま、主調整+300ms、ユーザー位置15.3秒を推奨する。既に100ms分採用後に合計300msになったなら、残り200msだけを加える。

候補は操作履歴からの目安であり、実際にその量だけ音声が移動したことや、次回の成功を保証しない。旧「今合ってる」は現在位置そのものを次回の基準タイムラインへ保存する別操作として維持した。

## 診断・比較手順

1. 開発者向け設定でS=0／500ms、事前シーク無効／有効を比較する。事前シークは事前再生方式のみ。
2. 動画、基準位置、トリガー、音量・継続時間、マイク保持、端末とイヤホンを揃え、試行順を入れ替える。
3. 診断パネルで現在の最大30試行の設定別統計を確認し、区切りごとにJSONを保存する。
4. 複数JSONを診断パネルのローカル集計へ読み込む。最大20件・各5MiB・合計10MiB。通信・曲設定への取込はしない。
5. 完了した試行を保存する。同じrunIdと試行IDは二重計上せず最初のJSONを優先する。不正形式は拒否理由を表示する。runIdを持たない旧診断JSONと検証ページJSONはこの集計の対象外。
6. 同じ物理設定、UA、配信元、実／模擬モードごとに平均、母標準偏差、最小、最大、最大最小差、中央値、p95を比較する。20試行未満は探索的参考値と表示する。Bluetooth経路はブラウザから確定できず、同じUAでも同条件とは限らないため観察メモを併用する。

主な時刻はtriggerMs、playRequestMs、playingEventMs（受信観測）、playingConfirmedMs（現在状態の確認完了）、plannedRequestMs。PLAYING受信を実発音とみなさない。予定要求時刻との差をplannedRequestSlipMsとしてJSONへ出す。省略したseekを実行したようにログへ記録しない。

## 実機で残る確認

iPhone Safari＋BluetoothでのS変更・事前シーク・再開成功・待機中の無音・出力先・音切れ・ループは未確認。WebのタイマーやYouTubeのシーク／バッファリングにより、Sが同じでも実発音時刻は変わり得る。[YouTube公式仕様](https://developers.google.com/youtube/iframe_api_reference)上のシーク動作からも微小な位置移動の精度を断定できない。

実機ではまず既定の0ms／事前シーク無効で回帰確認し、次にSだけ、最後に事前シークを変えて比較する。200msの継続検知による遅れは別要因として記録する。API上の標準偏差が小さくなっても実発音や聴感上の同期が改善したとは判定しない。実発音の客観測定には、IFrame API以外の検証方法が必要。
