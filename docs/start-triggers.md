# 開始トリガーの店舗比較

## 方式と操作

開始トリガーは曲・DAM／JOYSOUND／自宅テストごとに保存する。既存データの方式未指定は「伴奏検知」。
メイン画面の「開始トリガー」で選択する。変更は「すべて停止」後に限り、再生・検知・補正待機中は選択を無効化する。
切替だけでは登録開始位置、歌声用開始位置、発声合図用開始位置、しきい値・継続時間・補正・マイク方針を消さない。

| 方式 | 開始条件 | 基準となる動画位置 |
| --- | --- | --- |
| 伴奏検知 | 従来のRMSしきい値＋継続時間 | 登録開始位置 |
| 歌声トリガー | 同じRMSしきい値＋継続時間 | 本人動画の歌い出し位置 |
| 発声合図 | 同じRMSしきい値＋継続時間 | 合図に対応する動画開始位置 |
| 手動開始 | 準備完了後の「この位置から開始」 | 登録開始位置 |

歌声・発声合図は音量による実験上の呼び分けであり、歌声・話者の識別、合図の言葉の認識は行わない。
伴奏や雑音でも反応する。同じしきい値・継続時間を使い、既存のしきい値提案も雑音と伴奏の音量比較である。
声の合図に適した値かは別途実測する。特定の方式を最適とは決めていない。

### マイクを使う3方式

1. 曲・利用環境・トリガーを選び、歌声／発声合図なら対応する動画位置を入力する。
2. 4段階の±5秒／±1秒／±0.1秒／±0.01秒で実効開始位置を調整し、必要なら設定を保存する。
3. 事前再生方式で「検知を準備」→YouTube内を直接タップ→自動一時停止→マイク取得→RMS検知待機。
4. 目的の伴奏・歌い出し・発声を入力する。初回の開始条件成立は1回だけ受け付け、補正待機・シーク・再生要求へ進む。
5. PLAYING確認・実際のBluetooth出力をそれぞれ観察する。次の試行の前に停止する。

### 手動開始

1. 「手動開始」と事前再生方式を選び、「手動開始を準備」を押す。
2. YouTube内を直接タップして事前再生する。自動一時停止確認後に「手動開始待ち」になる。
3. 目的の時点で「この位置から開始」を押す。同じ固定待機・位置補正・範囲制限を通して初回再生を要求する。
4. クリック連打やRMS入力からは二重要求しない。手動待機にも保存済みの有限期限を適用する。

手動開始ではマイクを取得せず、検知器を起動しない。メーターは未取得表示となる。保持／解放の保存設定は残すが、この試行ではマイクを使わないことをJSONへ記録する。
マイクを使う方式とBluetoothの音声経路・発音遅延が異なる可能性があるため、同条件と仮定せず出力先・音質を観察する。
従来方式も残すが、Safariの制限が解決する保証はない。事前再生後でもブロックや失敗があり得る。
固定待機を使った手動開始はクリックから遅れて再生要求するため、直接クリックの再生許可と同等とは断定しない。
隠れた予備再生、音声抽出、公式API以外の制限回避は行わない。

## 位置計算と安全性

- 歌声・発声合図の位置が未指定なら登録開始位置を使う。各値は別フィールドで保持する。
- 選択した基準秒を整数msへ丸め、既存オフセットを加え0以上へ制限し、有効Bと主調整msを各1回だけ加える。
- 4段階の主調整は全方式で共通のstartAdjustmentMs。方式ごとの主調整を自動複製・初期化しない。
- 新しい3方式では初回要求時に0〜動画長へ制限する。動画長が取得できない場合は安全にエラー終了する。
- 既存の伴奏検知の分岐・従来方式のcue動作は維持し、事前再生／補正があるときの既存範囲制限も維持する。
- 初回トリガーは1セッションにつき1回。一時停止後の「再生」は既存機能として別の明示要求であり、再検知や再シークはしない。
- 新しい方式で固定待機を一時停止し、まだ初回要求前に「再生」した場合だけ、選択位置を一度適用して再開する。取り消した待機タイマーを復活させない。
- 停止・曲変更は既存の世代無効化とタイマー取消・資源解放を通す。手動開始待ちでiframeを再び直接再生した場合も、想定外再生として停止する。
- 10msは設定刻みであり、Bluetooth実発音や同期精度の保証ではない。

## v3保存・移行

旧アプリが新トリガーを無視して別の位置・方式で再生しないよう、通常アプリの保存先とバックアップをv3へ拡張した。

- 曲リスト: karaokesync.app.library.v3 / バックアップ {format:"karaokesync-library-v3",version:3,songs:[...]}
- 手入力設定: karaokesync.app.sync-preferences.v3
- プロファイルの追加項目: startTrigger、vocalPositionSec、cuePositionSec。startTriggerの値はaccompaniment/vocal/cue/manual。
- v3が未作成のときだけv2、さらに未作成ならv1を読み取る。起動・選択では保存せず、明示保存時だけv3へ一括書込する。
- 旧キー・旧HTMLデータは削除・上書きしない。v3が空でも旧曲を復活させず、破損v3から旧データへ黙って戻らない。
- Reactv2/v1・旧HTML0.6のJSONは従来のプレビューと個別上書き確認を経て取り込める。
- 旧データは伴奏検知として扱い、声用の開始位置を推測して保存しない。
- 旧アプリはv3を扱えない。旧版へ戻す場合は保護した旧キー・旧バックアップを使う。v3作成後に旧版で編集した内容は自動同期しない。

## 診断JSON

診断ログパネルの「開始トリガー比較JSONを保存」で直近30試行を出力する。既存の「診断JSON」にも比較情報を含める。
試行ごとに準備時の動画ID・利用環境・トリガー・位置と補正・保持方針を固定して記録する。

- triggerMs: 検知成立／手動開始受理時刻。RMS観測時刻はsourceSampleMsで別記。
- playRequestMs: 初回再生要求時刻。
- playingConfirmedMs: 事前再生ではなく、初回要求後のPLAYING実状態確認時刻。
- seekSec、playingPositionSec: 指定シーク位置と、取得できた場合のPLAYING時点の位置。
- triggerToRequestMs、triggerToPlayingMs、requestToPlayingMs: API上の各差分。
- outcome: pending/api-playing/failed/timeout/blocked/stopped/ended。
- termination: 後の停止・終了・エラー理由。再生成功後に停止しても初回API再生成功の記録は残す。
- initialRequests/resumeRequests: 初回要求と後の明示再開の回数を分離。
- microphoneUsed、retainMicRequested、microphoneReleasedMs、cleanupComplete/cleanupFailure: マイクの設定・実使用と後始末。

30試行を超えた破棄件数はdroppedに記録する。画面再読込で消えるため比較後に保存する。
時刻はperformance.now()のms、timeOriginMsはブラウザ時刻基準。録音や実際の発音時刻は保存しない。
api-playingはAPI上の確認であり、イヤホンから実際に鳴った時刻や聴感同期の成功とは区別する。

## 店舗での未検証項目

iPhone Safariの今回の4方式切替、歌声／合図位置、手動開始、Bluetooth経路、長時間待機、v3保存・JSON出力は実機未確認。
店舗の伴奏・隣室音・拍手・他人の歌声による誤検知、本人の声への反応、方式間の再現性と実発音遅延・同期精度は現場で比較する。
