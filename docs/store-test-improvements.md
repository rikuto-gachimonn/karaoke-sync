## 調査と変更

- config/settings.ts、library/model.ts: 通常アプリの未保存設定をしきい値0.035・200msに変更。検証ページ用の従来既定値0.08・50msは維持。保存済み値をロードする処理は変更しない。
- session/controller.ts、session/state.ts: 検知後待機、歌唱中seek、現在位置取得、調整量、通知、マイク異常の処理を追加。再生開始後のマイク異常や解放失敗だけを理由に動画を停止する処理を変更し、解放失敗は警告と全停止による再試行を維持。

## 負の位置と遅延

新しい開始計算は次のとおり。

```
rawMs = 選択トリガーの保存位置ms + 既存オフセットms + 有効B補正ms + 主調整ms
seekSec = max(0, rawMs) / 1000（実行時に動画長へ制限）
waitMs = 有効A固定待機ms + max(0, -rawMs)
```

開始0秒・主調整-1000msなら、検知成立から1000ms待機し0秒から再生する。準備時から待つわけではない。停止・曲変更・エラーでは世代無効化とタイマー取消を行う。検知は1回だけ消費する。負の既存Bやオフセットも新しい負位置ルールの対象となり、以前0に丸められた保存値は、値を変えずに待機へ解釈される。正の範囲では従来の計算を維持する。旧データの保存形式変更・自動上書きはない。

200msの継続時間は観測開始から判定までの遅延を含む。これを全曲へ機械的に加算していない。RMS検知は歌声・話者・言葉を識別せず、周囲の音でも成立し得る。

## 操作

1. 曲と環境、開始トリガーを選ぶ。保存済み設定があればそちらを優先する。
2. 停止中に「実効開始位置の調整」を開く。50ms操作を含め符号付きの値を設定し、必要なら曲・環境の設定を保存する。
3. 従来どおり準備→YouTube内を手動再生→自動一時停止→マイク検知。メーターと上部の通知を確認する。
4. 再生中は歌唱中の±50ms/100ms/1秒を使用する。seekのみを要求し、追加のplayやマイク取得を行わない。自動追従補正はしない。
5. 「今回の調整を次回用に保存」は今回の移動要求の合計を準備時の開始設定へ一度だけ加算して明示保存する。同じ合計で何度保存しても二重加算しない。画面の開始設定も更新し、次回準備から利用する。実際のシーク量・聴感上の成功を保存したと保証するものではない。
6. 「今合ってる」は現在の動画位置を次回トリガー時の開始位置として明示保存する。曲途中の位置を保存すると次回もその位置から始まる。移動要求合計の保存とは意味が異なる。
7. 全停止で検知・プレイヤー・マイクを終了する。タイムアウトや異常は状態と上部通知へ残る。

保存先は既存の曲・DAM/JOYSOUND/HOME別設定か、手入力動画の既存v3設定領域。既存JSONバックアップ・復元を利用する。保存に失敗した場合は成功表示や設定更新を行わない。

## 通知とマイク異常

正常な検知開始・検知成功・ユーザー停止・異常終了を通知する。異常はonInterruptedの購読を外して重複通知を防ぐ。検知待機中の異常は安全にセッション終了。検知成功後の異常は監視を止めてマイクを解放し、待機済みの再生予定／既に開始した動画を継続する。マイク解放が失敗した場合も動画は継続し、警告を表示して全停止で再試行できる。YouTube側のエラー・ブロックや全停止は従来どおりセッションを終了する。

Bluetoothの接続や出力先の変更を直接確認したとは表示しない。Web APIから確認した入力終了・AudioContext中断のみ通知し、実際のイヤホン接続と出力はユーザーが確認する。

## 実機検証と残る課題

YouTubeの[公式仕様](https://developers.google.com/youtube/iframe_api_reference)ではシークがキーフレーム等の影響を受ける。50ms/10msの設定・要求はその精度の保証ではない。250ms/1000ms後のAPI位置をplayer.live.seek.observedへ記録するが、その間に動画は進行するため、単純な差はシーク誤差ではない。実発音時刻も測定していない。

[MediaStreamTrack ended](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/ended_event)は入力終了を通知するが、stop()での終了は同イベントを発生させない。Bluetooth物理切断や出力先切替が必ず通知されるとは限らない。音声ループ・停止の原因は今回のPC模擬検証で特定できていない。iOSネイティブ側の音声セッション管理を検討する余地はあるが、YouTubeやBluetoothの問題が必ず解決するとは言えない。

iPhone＋Bluetoothで以下を順に確認すること。

1. 既存の事前再生から検知再開までの回帰、出力先・無音・音質・ループの有無。
2. 0秒/-50ms/-1000ms、A固定待機との併用、待機中の全停止。診断ログで検知→待機→seek→play→PLAYINGの順を確認。
3. 再生中±100ms、次に±50ms。音切れ・BUFFERING・意図しない停止・連続操作時の実際の移動を観察。
4. 今回の調整を保存→全停止→次回準備。曲・環境別保存とバックアップ復元を確認。
5. 0ms/200ms前後の継続時間、低い歌い出し、突発音と伴奏の誤検知。200msを最適値とは扱わない。
6. 待機中／再生中のイヤホン取り外し。通知された事実、動画が継続するか、マイク資源と出力先を別々に記録。

実YouTubeでの微小シーク・iPhone Safari・Bluetooth・聴感上の同期精度は未検証。PC模擬成功をこれらの成功扱いにはしていない。
