# URL入力の一本化と補正リセット

## 入力欄の調査・変更

通常アプリには、曲管理の再生動画URL/ID、PC伴奏の記録URL/ID、詳細設定の未登録動画URL/IDの3つの入力経路があった。PC伴奏欄は`accompanimentRef`というメタデータの記録専用であり、PC上の動画やYouTube APIを操作する機能ではなかった。詳細設定の`ManualVideoInput`は曲を登録せずに動画を使い、動画・機種別の設定を保存するUIだった。

- 曲管理の共有`VideoReferenceInput`を唯一のURL入力欄として残した。PC/iPhoneで同じURL正規化・ID抽出・検証・曲情報保存を使用する。
- PC伴奏の編集入力と専用説明を削除。既存の`accompanimentRef`はデータ・バックアップにそのまま残し、保存済み曲の閉じた参照欄で閲覧できる。曲名等の編集でも値を保持する。
- 詳細設定の重複入力・確定ハンドラーと、不要になった`ManualVideoInput`コンポーネントを削除。プレイヤー/デバッグ内部処理、動画別の旧設定キーは削除しない。以前の手入力動画は同じIDを曲登録すると既存の`initialProfiles`処理で保存設定を引き継げる。
- 「この曲を登録」（編集時は「曲情報を更新」）をURL入力ラベルの直後へ配置。曲名・任意アーティストはその上、入力形式の案内・タイトル再取得・登録通知はボタンの下。元の同じformのsubmitを使い、必須曲名・重複登録防止・成功/失敗通知・登録後の選択を維持する。
- 保存キー/形式・移行処理を変更せず、表示変更だけで保存済み曲を更新しない。

## 開始位置の「補正を0秒に戻す」

通常画面の開始位置調整が変更するのは`startAdjustmentMs`（主調整）。`resetStartAdjustment()`はこの値だけを0にした編集中の入力を返す。曲の基準位置、歌声/伴奏別の位置、旧`offsetSec`、比較補正A/B、安定化待機S、検知継続時間Dと自動補正ON/OFF、採用履歴を変更しない。

既存の`playbackPlan()`で再計算するため、主調整を0にしても旧オフセットやB、自動補正D等が存在すれば実効位置は基準位置と一致しない。UIに「主調整だけ」を戻す旨と、旧補正を維持する旨を明記した。二重計算や新しい同期式は追加していない。

操作だけでは保存しない。「この設定を保存」を押した時に従来どおり現在の曲・機種・モードへ保存する。手動モード切替では既存の編集中モード別ドラフトを維持し、別モード・機種の保存値を変更しない。準備中/再生中など設定を変更できない時は無効、主調整が既に0なら無効にする。

## リアルタイムの「今回の補正を0秒に戻す」

`resetLiveAdjustment()`は現在セッションの累積要求量Tの逆符号を、既存のシークと履歴記録の共通処理へ渡す。累積が5秒を超えていても、リセットは逆方向への1回の要求とする。通常の±0.05/0.1/1/5秒ボタンの上限は5秒のまま。

```
要求差分 = -T
目標位置ms = clamp(現在のAPI位置ms - T, 0, 動画長ms)
範囲内の要求量 = 目標位置ms - 現在のAPI位置ms
新しい累積 = T + 範囲内の要求量
```

例えば+1500msなら現在位置から-1500ms、-500msなら+500msを要求する。基準開始位置へは戻さない。動画端で不足する場合は累積を偽って0にせず残量を保持・通知する。後で範囲内に移動した際、再度残量を取り消せる。シークに失敗した場合は合計・履歴を更新しない。再生中以外/合計0では操作不可。

- 逆向きシークも既存`player.live.seek`と試行の`liveOperations`へ追加し、要求差分・範囲内差分・元位置・目標・時刻を記録。過去の操作は削除しない。
- 追加の`player.live.reset`ログに残量を記録。UI合計と試行合計は同じ値を使う。表示時刻は既存のAPI観測で更新する。
- 既存`LiveHistory`は操作履歴がある合計0の結果も保持する。未採用なら次回推奨差分も0。既に+1500msを次回用に保存した後で今回の合計を0に戻すと、採用済み記録との残差は-1500msになる。これは提案として表示するだけで、再度明示保存するまで曲設定を更新しない。
- APIへのseek要求と範囲制限の整合性を記録する。YouTubeの実際の着地点やBluetoothの発音精度を測定・保証するものではない。
